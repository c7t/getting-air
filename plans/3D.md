The headline, so it can be argued with before reading 400 lines:

- **The raw cell-update rate barely changes — and MEASURED it is better
  than predicted.** 2D measures **1.80 GLUPS** on the desktop for a whole
  AMR frame; a dense 3D D3Q19 solve measures **3.62 GLUPS / 551 GB/s =
  77% of the 4080's peak bandwidth** (sec 2.4). The prediction was
  0.9–1.7 GLUPS *after* coupling overhead; applying 2D's own measured
  coupling fraction to the measured solve rate gives **1.6–2.0 GLUPS**.
  See "Why 3D lands at roughly the same LUPS" for why this is not a
  coincidence.
- **What changes is how many cells you need.** Matched physics costs
  ~35–60x more cell-updates in 3D, so wall-clock per unit of physical
  time goes up by about that factor. Interactive-at-60fps becomes
  ~1 macro-step per displayed frame instead of 64.
- **AMR earns far more in 3D than in 2D.** Against a dense grid at the
  same finest resolution, 3-level AMR saves ~**32x in time and ~20-30x in
  memory** in 3D, against ~15x/~3.4x in 2D. This is the actual argument for
  doing the fork at all: the dense 3D configuration that would be
  interesting (512^3) is not merely slow, it does not fit in memory.
- **Build with the RING. Ghost-free is not being done** -- settled
  2026-09-09 and not open (sec 2.1). It was built and measured in 2D
  (`plans/ghost-free.md`, branch `perf/ghost-override`): 5-9% at N=3
  against a ~10% measurement floor, plus a corner-balance refinement
  constraint the codebase never had, plus giving up the ring's graceful
  degradation while refinement converges. The win did not materialize and
  the complications did. The memory argument that was its other leg is
  moot -- there is headroom (sec 2.2, sec 3.5). Attack the 70% dispatch
  waste separately, by not STEPPING ghost cells.
- **D3Q27 costs 1.54x D3Q19** (measured, sec 2.4 -- slightly worse than
  the 1.42x byte ratio predicts, because Q27 also sustains a lower
  fraction of peak bandwidth) and is not worth it as the default. Ship
  D3Q19; keep Q27 as a `?q=27` build variant, using the same both-paths-
  in-one-build mechanism as `?ghostcopy=`.
- **This is a desktop-only page.** The realistic target config wants
  ~0.7–1.0 GB of GPU buffers and the raised-limit path. The PowerVR phone
  gets a toy config at best.

## 1. What already transfers, and what has to be rebuilt

### 1.1 Transfers essentially unchanged (design, not code)

These are the parts of this codebase that are dimension-agnostic and
already paid for. They are the reason a 3D fork is a project and not a
rewrite.

| Asset | Why it transfers |
|---|---|
| `S_Advance` recursion (`main-amr.js:2170`) | Pure temporal scheduling. Root steps once, non-root steps twice and drives its child twice. Nothing in it knows the dimension. Verbatim. |
| Pool indirection (`blockSlot`/`slotToBlock`/`freeList`/`parentSlot`/`quadrant`) | Slot allocation is a free-list over opaque slots. Only `N_CHILDREN` 4 -> 8 and the quadrant->octant decode change. |
| `DIRECT_GHOST` streaming | Already implemented, already validated, and worth **far more** in 3D — see §2.1. This is the single most valuable thing the 2D work bought the 3D fork. |
| Dupuis–Chopard `fneq` rescale, `tau_fine = 2*tau_coarse - 0.5` | Dimension-independent. Verbatim. |
| Raised-limit request pattern (`main-amr.js:776-805`) | Already handles `maxStorageBufferBindingSize`, `maxBufferSize`, `maxStorageBuffersPerShaderStage` with a loud failure path. 3D needs all three raised further; the mechanism is there. |
| SoA `f` layout `f[i*NCELLS + cell]` | Per-direction planes are separate strides, so a 3D `f` too large for one binding splits by direction with no addressing change. |
| f16 packing (`common_fpack.wgsl`, `f-pack.mjs`) | Transfers *structurally* (it already handles an odd Q, 9 -> 5 words; 19 -> 10, 27 -> 14 with the same lo/hi/word helpers) but see §2.2: it is dead on accuracy and 3D does not revive it. | Validation architecture | `tools/validate-all.js` owning the Chrome lifecycle, `tools/lib/*-metrics.js` shared between leaf tools and the aggregate harness, boot-smoke against every page, `make check`. All of it. |
| `?bench=1` / `?telemetry=1` / `?benchSkip=` | Pass-group attribution is structural, not 2D. Same groups exist in 3D. |
| **AGAL itself** | `AGAL/` in this repo already implements **D2Q9, D3Q19 and D3Q27** over the same AMR algorithm (`AGAL/inc/solver_lbm.h`, `AGAL/src/Makefile` `VSET=`). The reference this project traced for `S_Advance` has already answered the 3D questions in C++. Read it before designing, not after. |

### 1.2 Mechanical translation (bounded, tedious, low-risk)

Cell indexing `y*W + x` -> `z*W*H + y*W + x` everywhere; `vec2` -> `vec3`;
`dispatchWorkgroups(WGX, WGY)` -> a 3D shape (see §2.4); `@workgroup_size(8,8)`
-> `(4,4,4)`. Affected: every shader that touches a cell index, which is
all of them.

- `common_lattice.wgsl` — **DONE** (2026-09-09), built alongside M0
  because M0 needed it. `lattice-3d.mjs` derives both velocity sets rather
  than typing them: enumerate `{-1,0,1}^3`, bucket by shell, emit each
  velocity immediately followed by its own negation. Three properties fall
  out and are relied on downstream — `opp` is structural (no table to
  transpose), **D3Q19 is a strict index-prefix of D3Q27** (so `?q=19|27` is
  a loop bound, not a remap), and the shell boundaries are exact (so "D3Q19
  never needs a corner neighbour", §2.3, is readable off the index).
  `shaders/common_d3q{19,27}_lattice.wgsl` are generated from it by
  `tools/gen-lattice-3d.js` and checked in (there is no build step);
  `tools/test-lattice-3d.js` guards them two ways — exact drift against the
  generator, *and* the lattice moment conditions (0th–4th) plus a
  searched-not-assumed `opp` involution computed from the tables **parsed
  back out of the WGSL**. The second half is the one that fails when
  generator and file are wrong together; both halves were negative-tested
  against a deliberately transposed `opp` and a mis-shelled weight.
- `common_sponge.wgsl` — add the z distance. Trivial.
- `common_walls.wgsl` — wall-normal axis becomes a parameter, or duplicate
  for y and z. Small.
- `lbm_*.wgsl` (dense base) — direct translation of the fused step.
- `amr_average_*.wgsl` — 4-cell average -> 8-cell average.
- `amr_criterion*.wgsl` — see §1.3, the criterion itself changes.

### 1.3 Genuinely new work

**The rigid body goes 3 DOF -> 6 DOF.** `CardState` (26 f32 today) gains
z, a quaternion (or rotation matrix) instead of `theta`, a full 3x3
inertia tensor, and 3 torque components. `physics.wgsl`/`amr_physics.wgsl`
are `@workgroup_size(1)` and stay that way, but the integrator becomes
quaternion + `I_world = R I_body R^T` with the gyroscopic term
`omega x (I omega)` — which is exactly the term that makes a falling plate
in 3D interesting (tumbling vs. fluttering vs. chaotic modes) and which
has no 2D analogue at all. Budget this as its own milestone; it is where
the physics actually gets richer, not just bigger.

**Force/torque reduction.** `common_reduce.wgsl` reduces 3 scalars
(fx, fy, tz) today. 3D needs 6. Mechanical, but it touches every force
kernel and their bind groups — i.e. the exact 238e48c failure surface
CLAUDE.md warns about.

**Refinement criterion.** 2D refines on `|omega|`, a scalar. In 3D
vorticity is a vector and `|omega|` flags every shear layer including the
boundary layer everywhere, which will refine far too much. Use the
**Q-criterion** (`Q = 0.5*(|Omega|^2 - |S|^2)`), which is what AGAL
offers as `S_CRITERION=1` for exactly this reason. This changes
`amr_criterion*.wgsl` substantively — it needs the full velocity gradient
tensor, 9 components, not one curl.

**Geometry SDF.** Ellipse -> ellipsoid or (better, for a "card") a
rounded box / flat plate SDF. The true-signed-distance lesson from
`common_geometry.wgsl`'s header applies with more force in 3D: an
algebraic distance on a 3-aspect-ratio body distorts the chi band and the
refinement margin anisotropically along *two* axes now. Write the true SDF
from the start.

**Rendering.** This is the largest single new piece and it has no 2D
analogue at all. Three options, in the order they should be attempted:

1. **Axis-aligned slice** — reuse `render.wgsl`/`amr_render.wgsl` nearly
   verbatim on a z-slice, with a slider. Nearly free, and it is what you
   want for debugging seams anyway. **Milestone 1's visual.**
2. **Resample-and-raymarch** — one compute pass per frame reconstructs the
   AMR hierarchy into a dense `r16float` 3D texture of Q-criterion (or
   speed), then a fragment shader raymarches it with a transfer function.
   Decoupled from the AMR machinery, ~256^3 x 2 B = 32 MB, and the
   reconstruction is the GPU sibling of `tools/lib/field-reconstruct.js`
   which already exists and is already unit-tested. **This is the right
   default.**
3. **Isosurface** — marching cubes on Q-criterion. Best-looking for vortex
   structure and what a 3D falling-card demo really wants to show. Real
   work (compaction, indirect draw). Explicitly out of scope for v1.

Do **not** attempt to raymarch the quadtree/octree pool directly. It is
accurate and it is a research project.

## 2. The four decisions 3D forces, that 2D never did

### 2.1 Tile size and materialized ghosts — the big one

A level-m tile covers `RB^d` parent cells and holds `(2*RB)^d` fine cells,
padded by `GHOST=2` per side to `FB = 2*RB + 4`.

| RB | 2D interior / padded | 3D interior / padded |
|---|---|---|
| 4 | 64 / 144 (**2.25x**) | 512 / 1728 (**3.38x**) |
| 6 | 144 / 256 (1.78x) | 1728 / 4096 (**2.37x**) |
| 8 | 256 / 400 (**1.56x**) | 4096 / 8000 (**1.95x**) |

At today's RB=8, 36% of a 2D tile is ghost shell. In 3D the *same* RB
makes it 49%, and at the RB=4 that memory forces (below) it is **70%**.

`plans/perf-characterization.md` measured the ghost *ring* as ~1% of
frame time in 2D and concluded the FB 20->16 shrink wasn't worth it. **Do
not carry that conclusion into 3D.** The finding was about compute time;
the 3D problem is *memory*, and there the shell is 70% of the pool:

#### The scaling law

The clean way to see this is **cells stored per coarse cell covered**,
which is `(FB/RB)^d` — a tile covers `RB^d` coarse cells and allocates
`FB^d`. The ideal (no padding at all) is 4 in 2D and 8 in 3D:

| config | FB | 2D `(FB/RB)^2` | 3D `(FB/RB)^3` | 3D shell |
|---|---|---|---|---|
| RB=4, GHOST=2 | 12 | 9.00 | **27.0** | 70% |
| RB=6, GHOST=2 | 16 | 7.11 | **19.0** | 58% |
| RB=8, GHOST=2 | 20 | **6.25** *(today)* | **15.6** | 49% |
| RB=4, GHOST=1 | 10 | 6.25 | 15.6 | 49% |
| **any RB, ghost-free** | 2*RB | **4.00** | **8.00** | 0% |

Today's 2D build sits at 6.25 against an ideal of 4 — 56% overhead, which
nobody has had a reason to care about because the 2D pools are ~11 MB.

#### DECISION, FINAL (2026-09-09): build 3D with the RING

**This section used to say "go ghost-free from the start, RB=4, FB = 2*RB."
That is now withdrawn.** It rested on a memory argument later walked back to
~2x (roughly a wash against RB=8-with-ghosts once its over-refinement is
counted) and on a compute argument that had not been measured. It has now been
built and measured in 2D -- `plans/ghost-free.md`, and the branch
`perf/ghost-override` -- and the answer is:

    N=3, pinned body, 9 reps x 4000 macro-steps:  ghost-free is 5-9% faster
    against this harness's own stated ~10% desktop floor.

Three things that measurement established, none of which were in this plan:

**(i) The win is dispatch waste, not cheaper interpolation.** The ring path
dispatches 400 cells per tile to update 256, and runs an interp pass on top.
The inline gathers cost roughly what they replace: measured **~82,000 parent
fetches per macro-step, about +67% on raw `f` reads**, and ghost-free is still
net faster ONLY because the parent tiles stay cache-resident.

**(ii) Corner-inclusive 2:1 balance turns out to be MANDATORY.** Nothing in this
codebase ever guaranteed a tile's diagonal neighbour existed at the same level
-- the refine gate says "edge-neighbors", the cascade scans a ring of 8, and
debugCheck21Balance used [N,S,E,W]. The ring absorbs that (interp fills a corner
ghost from the parent); the ghost-free bilinear stencil reads the parent's
corner cell directly and cannot. Measured before the fix: the fallback clamp
fired on 0.3% of inline-parent samples, steady, and **100% of them diagonal**.
So ghost-free is not a storage change -- it imposes a refinement constraint.

**(iii) The ring does a THIRD job this plan never counted.** Not just storage
and memoization: it is *graceful degradation for a lagging refinement
structure*. Interp always fills it from whatever the parent currently is, so an
unconverged topology yields stale-but-valid data. Ghost-free converts that into
a hard precondition that must hold at the instant of use -- against a cascade
`amr_manage_pool.wgsl`'s own header records as not always converging within a
round.

#### How each of those scales to 3D

| | 2D | 3D | direction |
|---|---|---|---|
| dispatch waste (the win) | 36% | **70%** at RB=4 | **better** |
| boundary cells per tile | 23% | **58%** at RB=4 | worse |
| cache-residency of the redundant fetches | holds | large working set, D3Q19 | worse, and the win DEPENDS on it |
| corner-balance neighbourhood | 8 (cross -> box dilation) | **26** | much worse |
| refinement-lag exposure | falling card | tumbling body, more levels | worse |

One half improves; three or four degrade -- and the one the measured win
actually depends on, cache residency of the redundant parent fetches, is
exactly the one 3D is most likely to break. Corner balance is the sharpest:
in 2D it cost +4 L1 tiles (~12%); in 3D it means dilating the refined region by
a full 26-neighbourhood BOX rather than a 6-face cross, plausibly 1.3-1.7x more
tiles, against a win that is ~10% at best.

#### So: RING for 3D v1. RB chosen on geometry fit, GHOST=2.

Get it correct first, against validation apparatus that does not exist yet,
with a coupling scheme that degrades gracefully while refinement converges
around a moving body.

**This is settled and is not to be re-argued.** The performance win did not
materialize when measured, the complications did, and the memory pressure that
was its other leg is not real: §3.5's target config wants ~0.7-1.1 GB against
16 GB of card, so the ~2x the ring costs is headroom being spent, not a
fits/doesn't-fit threshold. Ghost-free comes back onto the table only if some
future configuration makes memory the ACTUAL binding constraint AND the 3D
validation apparatus exists by then -- it is a numerical-scheme change at the
interface, and 3D currently has nothing that would catch a bad one. Worth knowing how that failed here: the level>=2
coordinate-space bug (Cd -5815) was caught by `amr-N3-diffuse`; the analytic
TGV gate passed straight through it, because TGV has no body and therefore no
geometry-forced refinement.

#### THE LEAD WORTH CARRYING FORWARD: don't STEP the ghost cells

The 70% dispatch waste is attackable without ghost-free, and this is the piece
of the whole exercise most likely to pay off in 3D.

In 2D, `?benchSkip=step1-ring` measured skipping ring threads at **0.2%
desktop / 0.9% phone**, because ring threads share their 8x8 workgroups with
interior threads and removing them frees no scheduling slot. **That reasoning
stops holding in 3D.** At FB=12 with a 4^3 workgroup there are 27 workgroups
per tile and the corner ones are ENTIRELY ghost. A compacted or indirect
dispatch that skips pure-ghost workgroups captures much of the dispatch-waste
win while keeping:

  - the ring's memoization (see (i) -- the redundant fetch problem disappears),
  - its graceful degradation for unconverged refinement (see (iii)),
  - and no corner-balance requirement at all (see (ii)).

It costs the memory ghost-free would have saved, which sec 2.2 establishes is
~2x and not a fits/doesn't-fit threshold. Measure the pure-ghost-workgroup
fraction first: at RB=4/GHOST=2 it is (27 - 8)/27 of the workgroups holding
(1728 - 512)/1728 = 70% of the cells, but the interior workgroups still read
ring cells, so the traffic saved is smaller than the cell count suggests --
which is exactly the 10x error the 2D traffic model made and this document
already records.

#### Why GHOST=2, if the ring is kept

`GHOST=2` is load-bearing, not slack. Each level takes two substeps per
parent step with no ring refresh between them (`S_Advance` interpolates
once per child *cycle*, and the parent's state does not change between the
child's own A and B, so re-interpolating would produce identical values).
Two layers let the ring self-advance: substep A's gather on a depth-1 ring
cell reaches into depth 2, so depth 1 is still valid for substep B.

After `DIRECT_GHOST` shipped, the ring serves exactly **one** case, which
`amr_step1.wgsl`'s own header states: a tile at a coarse/fine interface has
no same-level neighbour, so `blockSlot < 0` and the gather falls back to a
clamped read of a parent-interpolated ghost. Ghost-free replaces that
fallback with an **inline** parent reconstruction — the trilinear rho/u/`fneq`
plus Dupuis-Chopard rescale that `amr_interp_pool_parent.wgsl:275-286`
already computes, moved from a dedicated pass into the gather.

#### What it costs

Interface threads pay that reconstruction inline, potentially once per
direction. In 3D that is worse than it sounds: **58% of a tile's interior
cells touch the boundary at RB=4** (8^3 minus 6^3), against 33% at RB=8 and
23% in today's 2D RB=8 build. For a refined shell wrapped around a body a
large fraction of tiles genuinely are interface tiles, so this is not a
rare path.

`amr_interp_pool_parent.wgsl` also notes that a child's parent sampling
reaches into its parent's ring; with no ring at level 1, a level-2 tile at
its parent's edge must resolve into the parent's *neighbour* tile. Solvable
with the same `blockSlot` mechanism one level up, but it makes the
recursion more intricate.

One caveat against the compute claim above: `?benchSkip=step1-ring`
measured skipping ring threads at **0.2% desktop / 0.9% phone**, because
ring threads share their 8x8 workgroups with interior threads and free no
scheduling slot. In 3D with FB=12 and a 4^3 workgroup there are 27
workgroups per tile, several of them *entirely* ghost, so that result
probably does not transfer — but "probably does not transfer" is an
assumption, not a result. See §5, M0.5.

### 2.2 Memory, and WebGPU's binding limits

L0 is one dense grid. Its `f` buffer is `NCELLS * Q * 4` bytes:

| L0 | cells | D3Q19 per buffer | D3Q27 per buffer |
|---|---|---|---|
| 64^3 | 0.26M | 19.0 MiB | 27.0 MiB |
| 96^3 | 0.88M | 64.1 MiB | 91.1 MiB |
| **128^3** | **2.10M** | **152.0 MiB** | **216.0 MiB** |
| 160^3 | 4.10M | 296.9 MiB | 421.9 MiB |
| 256^3 | 16.78M | 1216.0 MiB | 1728.0 MiB |

The WebGPU **spec minimum** `maxStorageBufferBindingSize` is 128 MiB, so
128^3 D3Q19 is already past it. Three responses, in order of preference:

1. **Raise the limit.** Desktop NVIDIA adapters report far more than the
   spec minimum; `main-amr.js` already requests exactly what it needs,
   capped at the adapter's real capability, with a loud message on
   failure. Extend that, don't work around it.
2. **Split `f` by direction plane.** The layout is already SoA
   (`f[i*NCELLS + cell]`), so 19 planes can become 19 bindings — except
   `maxStorageBuffersPerShaderStage` is *also* a limit, and
   `amr_manage_pool.wgsl` is already at 16. Splitting into 4-5 groups of
   planes is the practical form.
**f16 is NOT a third option.** It halves everything and
`common_fpack.wgsl` already exists, so it will keep suggesting itself --
it is ruled out on accuracy, not on effort. `common_fpack.wgsl`'s own
header records mode 2 missing **every** analytic channel tolerance by
5-20x, and CLAUDE.md records it as "measured NOT viable as a default;
kept for re-measurement, not for shipping".

**Nothing about 3D revives it, and the reason is worth stating so it
isn't re-litigated.** The failure mechanism is that a finer grid spreads
the same physical gradient over more cells, shrinking the per-cell `fneq`
-- the entire information content beyond equilibrium -- toward the f16
quantum. So *the error grows with resolution*, and refining is what this
project does. That mechanism is dimension-independent: D3Q19/D3Q27
weights span a comparable range to D2Q9's (1/3 .. 1/36 against
4/9 .. 1/36), so the signal-to-quantum ratio is essentially unchanged.
3D also lands at a *finer* effective resolution (512^3 at Config B), which
is the direction that makes it worse.

Treat the memory budget in §3.5 as a hard f32 number. If it doesn't fit,
the answer is a smaller L0 or fewer levels, not a narrower `f`.

Realistic total for the target config (§3, L0=128^3, N=3, ghost-free
RB=4): **~0.7-1.1 GB** of GPU buffers. Comfortable on a 16 GB desktop
card, out of the question on the phone.

### 2.3 Neighbour topology: 4 -> 6 / 18 / 26

2D 2:1 balance checks 4 edge-neighbours; a padded ring needs 8 (4 edge +
4 corner). In 3D:

- **2:1 balance / refine gate**: 6 face-neighbours. Coarsen blocks on 8
  children instead of 4. Structurally the same code, wider loops.
- **A fully materialized ghost shell** would need all **26** neighbours
  (6 faces + 12 edges + 8 corners). This is genuinely nasty and is a
  second, independent argument for §2.1's ghost-free design.
- **`DIRECT_GHOST` gather** needs only the neighbours the lattice actually
  points at: **D3Q19 has 6 face + 12 edge directions and no corner
  directions at all**, so it never needs a corner neighbour. D3Q27 does
  (all 26). That is a real, concrete simplification that D3Q19 buys and
  D3Q27 gives back — worth weighing alongside the 1.4x bandwidth cost.

`amr_manage.wgsl` and `amr_manage_pool.wgsl` are the two largest and most
subtle shaders in the repo (340 + 492 lines, and their headers document
three separate live-verified bugs in the balance logic). **Expect the 3D
versions to be the hardest part of the port**, and expect the 2:1-balance
invariant checker (`debugCheck21Balance`, driven by
`tools/validate-amr-invariants.js`) to earn its keep immediately.

### 2.4 Dispatch shape and register pressure

**Dispatch.** 2D dispatches `(WGX1, WGY1, MAX_FINE_BLOCKS)` — tile extent
in x,y and slot in z. 3D has no fourth dimension. Fold slot into z:
`(FB/4, FB/4, (FB/4) * slots)`. With FB=8 and a 4^3 workgroup that is
`(2, 2, 2*slots)`, and `maxComputeWorkgroupsPerDimension` (65535) caps
slots at 32767. Fine, but it must be decided up front because it changes
every `gid` decode.

**Registers.** `lbm_step.wgsl` holds `f: array<f32,9>` *and*
`fo: array<f32,9>` live simultaneously — 18 f32. In 3D that is 38 (Q19) or
**54 (Q27)**, plus indices, geometry, and the neighbour-slot resolution.
Two consequences:

- Occupancy: an RTX 4080 SM has 64K registers and 1536 max threads. At
  ~96 registers/thread you get ~44% occupancy; a bandwidth-bound kernel
  wants more than that to hide latency.
- **Spilling.** A `private` array indexed by a loop variable is only kept
  in registers if the compiler fully unrolls. At Q=9 it does. At Q=27,
  through Tint -> SPIR-V/DXIL -> driver, it may not, and a spilled
  27-element array in scratch memory would be catastrophic and
  *silent* — it would look like "3D is just slow".

#### ANSWERED, 2026-09-09: registers are not a constraint

This was the #1 technical unknown and M0 retired it. `index-3d-spike.html`
(`shaders/d3_spike_q{19,27}.wgsl` over `common_d3_spike_body.wgsl`), driven
by `node tools/spike-d3-registers.js`. Dense periodic grid, no body, no AMR,
no render. Three kernel modes with **identical** memory traffic (Q planes in,
Q planes out per cell), so they are comparable in GB/s and only in GB/s —
GLUPS necessarily falls by 27/19 between the velocity sets, and reading that
fall as "Q27 is slow" is the mistake the tool prints a verdict to prevent.

RTX 4080 (nvidia/lovelace), 128^3 = 2.10M cells, `@workgroup_size(4,4,4)`,
20 dispatches per timed rep, median of 5, GPU timestamps. Repeat of an
identical row: **0.2%**, so everything below is well outside the noise:

| | GLUPS | GB/s | % of 717 GB/s peak |
|---|---|---|---|
| **D3Q19 full** (stream + collide) | **3.62** | **551** | **77%** |
| D3Q19 stream-only (access-pattern ceiling) | 3.58 | 544 | 76% |
| D3Q19 collide-only (coalesced, same registers) | 3.68 | 560 | 78% |
| **D3Q27 full** | **2.35** | **508** | **71%** |
| D3Q27 stream-only | 2.37 | 512 | 71% |
| D3Q27 collide-only | 2.51 | 543 | 76% |

**No spill, and nothing close to one.** Three independent readings:

- **The full kernel matches its own stream-only ceiling** (101% at Q19, 99%
  at Q27, both inside the repeat spread). The collision arithmetic and the
  38/54 live f32 are *free*: this kernel is purely bandwidth-bound.
- **Q27 sustains 92% of Q19's GB/s** in the full kernel and 97% in the
  coalesced collide-only kernel. A scratch-memory spill would show up as
  apparent bandwidth collapsing (spill traffic is real traffic the roofline
  cannot see), not as arithmetic getting slower. 92% is not that.
- **77% of peak.** The design premise in §3.2 — that 3D's much larger
  dispatches move the solver from 2D's 18% of peak toward 50–65% — was too
  conservative. It lands above the top of that band.

Two corollaries worth carrying:

- **D3Q27's real cost is 1.54x, not the 1.42x the byte ratio predicts**
  (3.623 / 2.352 GLUPS), because Q27 also sustains a lower fraction of peak.
  §4's recommendation gets slightly stronger, not weaker.
- **Workgroup shape does not matter here.** 4,4,4 / 8,8,1 / 8,4,2 / 16,4,1 /
  32,2,1 / 8,8,4 all landed within 2% (548–558 GB/s) at Q19, which is inside
  this harness's own spread. The occupancy concern above is real arithmetic
  but it is not the binding constraint at this problem size, so `(4,4,4)`
  can be chosen for index-decode convenience rather than tuned for.

Caveat on scope, so this is not over-read: the spike is a **dense, periodic,
uncoupled solve**. It says the per-cell kernel is healthy; it says nothing
about AMR coupling overhead (§3.2, risk #5), which is measured at 40–49% of
frame in 2D and is the remaining unknown in every throughput figure below.
Smaller grids are also worse — the same measurement at 96^3 gives 3.29 GLUPS
/ 501 GB/s at Q19 — so an AMR tile pool will not see 77% of peak.

The restructuring contingency (store only `f`, write planes as they are
computed, which `common_fpack.wgsl` forbids under f16 because two planes
share a word) is **not needed** and should not be built.

## 3. Performance

### 3.1 The measured 2D anchor

Desktop RTX 4080, `res=8&levels=3&blockage=3.3`, frozen at L1=125 / L2=144,
`plans/perf-characterization.md`'s ghost-copy A/B table: **616.5 ms per
4000 macro-steps = 154 us/macro-step.**

Cell-updates per macro-step: L0 65536 + L1 (125 tiles x 256 cells x 2
substeps = 64000) + L2 (144 x 256 x 4 = 147456) = **276,992**.

- **1.80 GLUPS**
- Traffic at 72 B/cell: 19.9 MB/macro-step -> **129 GB/s = 18% of the
  4080's 717 GB/s peak.**

Cross-check against live telemetry (`telemetry.log`, nvidia/lovelace,
res=8 levels=3): `gpuMs` 11.1–13.0 for 64 macro-steps = 174–203 us,
`l0Mlups` 323–376. Consistent; the bench number is faster because it
freezes refinement.

**18% of peak is the whole story.** The 2D solver is not bandwidth-bound;
it is bound by small dispatches, pass count and coupling overhead
(interp + avg + ghost = 40–49% of frame, measured, more than the fine
solve it serves).

### 3.2 Why 3D lands at roughly the same LUPS

Per-cell traffic, f32, A/B double buffer, read + write:

| set | Q | B/cell | solve-only roofline @ 60% of 717 GB/s |
|---|---|---|---|
| D2Q9 | 9 | 72 | 5.97 GLUPS |
| **D3Q19** | 19 | **152** | **2.83 GLUPS** |
| **D3Q27** | 27 | **216** | **1.99 GLUPS** |

Two effects pull in opposite directions and nearly cancel:

- **Down:** 2.1x (Q19) or 3.0x (Q27) more bytes per cell.
- **Up:** dispatches get 10–100x larger, so the fixed per-pass cost that
  dominates 2D amortizes and the solver moves from 18% of peak toward the
  50–65% a real streaming kernel achieves.

**The BW-efficiency half of that is now measured, not assumed** (§2.4):
the dense 3D solve lands at **77% of peak** (D3Q19) and **71%** (D3Q27),
above the top of the 50–65% band this section guessed at. So only the
coupling fraction is still an assumption — measured 40–49% in 2D at
levels=3, and expected **somewhat worse in 3D** because coupling work scales
with the tile's ghost shell (a surface) against the solve's interior (a
volume), and that ratio degrades with dimension.

Measured solve rate x assumed solve fraction:

| | conservative | tuned | (predicted, before M0) |
|---|---|---|---|
| BW efficiency | **77% (measured)** | **77% (measured)** | 45% / 65% |
| assumed solve fraction of frame | 45% | 55% | 45% / 55% |
| **D3Q19** | **1.63 GLUPS** | **1.99 GLUPS** | 0.96 / 1.69 |
| **D3Q27** | **1.06 GLUPS** | **1.29 GLUPS** | 0.67 / 1.19 |

Against 2D's measured 1.80 GLUPS. **The machine does about the same
number of cell-updates per second in 3D as in 2D** — the prediction held,
and the measured version of it is a little better than the guess. Every one
of those updates is worth less.

The one number here that is still a guess is the coupling fraction, and it
is now the ONLY guess: it moves D3Q19 between 1.63 and 1.99, and if it lands
at the 65%-of-frame that risk #5 worries about, at 1.27. That is the
measurement M3 should take first, with the `?benchSkip=` groups that already
exist.

### 3.3 What that buys, concretely

Assume a body + wake occupying a fraction of the domain. In 2D the
measured case is L1 = 12.2% of area, L2 = 3.5%. The same *linear* halo
thickness in 3D gives smaller volume fractions — a region of linear extent
L/3 is 11% of a 2D domain and 3.7% of a 3D one — so model L1 = 6%,
L2 = 1%, and show a generous variant too.

All figures below use the MEASURED solve rate (§2.4) with the assumed
coupling fraction band from §3.2: D3Q19 1.63–1.99 GLUPS. One standing
caveat: the measurement is on a 128^3 dense grid, and smaller working sets
do worse (96^3 gave 3.29 against 128^3's 3.62 GLUPS), so a pool of small
tiles will sit below this. Treat these as ceilings with a known-optimistic
lean, not as predictions.

**Config A — "first light", L0 = 64^3, N=2, L1 = 15%:**
- 262,144 + 2 x (0.15 x 262144 x 8) = **891k updates/macro-step**
- @ 1.63–1.99 GLUPS -> 0.45–0.55 ms -> **~1800–2200 macro-steps/s**
  (30–37/frame at 60fps)
- Effective finest resolution 128^3. Memory ~100 MB. Comfortably
  interactive — and small enough that the per-dispatch caveat above bites
  hardest here.

**Config B — the real target: L0 = 128^3, N=3, L1 = 6%, L2 = 1%:**
- L0 2.097M + L1 (0.06 x 2.097M x 8 = 1.007M, x2 = 2.01M) + L2
  (0.01 x 2.097M x 64 = 1.342M, x4 = 5.37M) = **9.48M updates/macro-step**
- @ 1.63 GLUPS -> 5.8 ms -> **~172 macro-steps/s**
- @ 1.99 GLUPS -> 4.8 ms -> **~210 macro-steps/s**
- D3Q27: divide by 1.54 (measured) -> **112–136 macro-steps/s**
- Effective finest resolution **512^3**. Memory ~0.7-1.1 GB (see §3.5).

**Config B, generous refinement (L1 = 12%, L2 = 2.5%):**
- ~20.4M updates/macro-step -> **80–98 macro-steps/s** (D3Q19).
  Refinement thresholds matter about 2x here. Budget real time for
  retuning them; the 2D thresholds will not transfer.

**Config C — dense 3D, no AMR** (worth stating, because it is the
baseline the fork has to beat) — **this one is now MEASURED, not modelled,
because it is exactly what M0 ran:**
- 128^3 dense D3Q19: **3.62 GLUPS, 0.58 ms/step -> ~1730 steps/s** (§2.4;
  the earlier estimate was ~870, off by 2x on the low side).
  A dense 3D base page is *comfortably interactive* and is 15% of the work.
  Build it first (§5 M1) and it is useful on its own. At Q27: ~1120 steps/s.

### 3.4 What ~190 macro-steps/s feels like

Take the cylinder-harness analogue: a body spanning 32 cells at the finest
level, U = 0.05, St ~= 0.2. One shedding period is
`D/(St*U) = 3200` finest-level steps = **800 macro-steps** at N=3.

- 3D Config B at 172–210 macro-steps/s: **3.8–4.7 seconds of wall clock
  per shedding cycle.** A 20-cycle time-average for Cd: **1.3–1.6 minutes.**
  (The pre-M0 version of this line said 8–17 s and 3–6 min, which did not
  follow from its own 101–180 macro-steps/s either — 800/180 is 4.4 s, not
  8. Both the rate and the arithmetic are corrected here.)
- 2D today, same arithmetic: ~5300 macro-steps/s -> **0.15 s/cycle.**

So the honest framing: **3D is ~25–31x slower in physical-time-per-
wall-second**, which turns "watch it flutter live" into "watch it evolve,
slowly, and leave it running for a real measurement". A 3D falling card
still *reads* as animated at ~190 macro-steps/s — it just falls in slow
motion relative to the 2D page. A 20-cycle Cd average in under two minutes
is a usable validation loop, which is a materially better position than the
3–6 minutes this section previously budgeted for.

### 3.5 The actual argument for AMR in 3D

Compare against a dense grid at the *same finest resolution*, remembering
the dense grid must take 4 steps to advance the physical time of one N=3
macro-step:

| | 2D (measured config) | 3D (Config B) |
|---|---|---|
| AMR updates / macro-step | 277k | 9.48M |
| dense-equivalent updates | 1.05M x 4 = 4.19M (1024^2) | 134M x 4 = 537M (512^3) |
| **AMR speedup** | **15x** | **32x** |
| dense memory, `f` only (a+b) | 79 MB (1024^2) | **20.4 GB** (512^3) |
| AMR memory, `f` only (a+b) | 23 MB | 0.7-1.1 GB |
| **AMR memory saving** | ~3.4x | **~20-30x** |

**In 2D, AMR is an optimization. In 3D it is the difference between a
configuration that exists and one that does not fit in a consumer GPU.**

(2D: L0 4.7 MB + L1 pool 384 slots x 400 cells 11.1 MB + L2 pool 256 slots
7.4 MB. 3D: L0 319 MB + L1 pool 2048-3072 ghost-free slots 159-239 MB +
L2 pool 3072-4096 slots 239-319 MB. Both count `f` only; velocity fields,
criterion and indirection add ~10-15%.)
That is the case for the fork, and it is much stronger than the 2D case
this project has been arguing with itself about.

### 3.6 Mobile

PowerVR at ~23 GB/s measured (`plans/perf-characterization.md`). D3Q19
solve-only roofline: 23e9/152 = **151 MLUPS**, call it ~75 MLUPS after
coupling. Config A (891k/macro-step) -> ~12 ms -> **~84 macro-steps/s**,

(Nothing in M0 touched the phone — the spike ran on the desktop only, and

## 4. D3Q19 vs D3Q27

| | D3Q19 | D3Q27 |
|---|---|---|
| bytes/cell (f32, a+b) | 152 | 216 (**1.42x**) |
| **measured dense solve** (§2.4) | **3.62 GLUPS / 551 GB/s** | **2.35 GLUPS / 508 GB/s** (**1.54x the time**) |
| projected GLUPS with coupling (tuned) | 1.99 | 1.29 |
| live registers for `f`+`fo` | 38 | 54 — **measured free, no spill** (§2.4) |
| `DIRECT_GHOST` neighbours needed | 18 (**no corners**) | 26 |
| Galilean invariance | cubic-order defect | isotropic to higher order |
| high-Re / LES behaviour | degrades; known artefacts in rotating and strongly 3D flow | the reason people pay for it |
| f16 word count | 10 | 14 |

**Recommendation: D3Q19 is the default; D3Q27 is a build variant.**

The velocity set should be a **compile-time `override Q`-style split**
producing two pipeline variants from one generated lattice table, selected
by `?q=19|27` — precisely the pattern `?ghostcopy=` and `?f16=` already
establish: both paths live in one build, so they are A/B-able for speed
*and* for physics from a single URL, and `tools/validate-all.js --extra=q=27`
sweeps the whole validation suite against the other one for free.

Do not reach for D3Q27 to fix an instability. If BGK at low tau is the
problem, **TRT or a regularized collision operator is the cheaper fix** —
same Q, same bandwidth, better stability — and AGAL already carries TRT
and MRT as `CollisionOperator` options to crib from.

**Angular MOMENTUM, not the explicit gyroscopic term.** §1.3 named
`omega x (I omega)`. That is correct but the worse of two equivalent
formulations: it needs an explicit cross product (a sign error there stays
invisible until a body tumbles) and conserves L only to truncation order.
Integrating L directly and taking `omega = R I_body^-1 R^T L` makes L
exactly conserved at zero torque, and the gyroscopic effect emerges from R
rotating inside I_world, which is where it physically comes from. Measured
on the GPU: **|L| drift exactly 0.00e+0** over 12500 steps.

**The rotation integrator needed a midpoint step, and this was not
optional.** For a free body L is constant but omega is not, and freezing it
at the start of the interval is first-order in exactly the variation that IS
the gyroscopic effect. Measured: **58.87% rotational-energy drift over 20000
steps, and a body spun about its MAJOR axis flipping** — an instability that
does not exist. |L| was exactly conserved the whole time, so no conservation
check would have caught it. Evaluating omega at the half step costs two
extra rotate-divide-rotates in a `@workgroup_size(1)` kernel and takes the
same measurement to **0.0052%**, with the stable axis stable and the
intermediate axis still flipping. `tools/test-d3-body.js` asserts all three.

**True SDFs from the start** (§1.3): sphere and rounded box are exact;
a spheroid reduces exactly to the 2D ellipse Newton in the meridional plane,
reusing the iteration `common_geometry.wgsl` already validated. A TRIAXIAL
ellipsoid is deliberately absent — its exact distance needs a 6th-degree
root, and an approximate one is precisely the trap that file's header
documents. "True distance" is asserted as `|grad phi| = 1` by finite
differences and against a brute-force nearest-point search over a
parametrically-generated surface, which shares no code with the closed
forms.

Measured 2026-09-09 (RTX 4080), all 10 body cases PASS:

| case | result |
|---|---|
| `spin`, GPU vs the f64 host reference | **3.4e-3 rad** (0.2 deg) after 12500 steps, body turned 3.06 rad |
| `spin`, |L| drift / |q|-1 | **0.00e+0** / 3e-8 |
| sphere Cd vs Schiller-Naumann, bounce-back | **+6.9% .. +12.8%** over Re = 20..200 at D=16 |
| sphere, refinement at Re=20 | 2.944 (D=16) -> 2.907 (D=24), reference 2.610 — converging |
| sphere lateral force / Cd | **1e-5 .. 3e-4** (vanishes by symmetry, as it must) |

The lateral-force check is the one worth keeping: it is independent of Cd,
and a transposed axis or a wrong torque in the six-scalar reduction shows up

`benchmarks/d3.json` rather than quietly scored against literature.

**THE SEAM ERROR WAS TWO PROBLEMS. One is fixed; the other is the one
this milestone named.**

**FIXED 2026-09-09: the grid transfers used the PRE-collision
Dupuis-Chopard factor on POST-collision populations.** `common_d3_step.wgsl`
and `common_d3_amr_step1.wgsl` are fused pull-stream + collide kernels, so
what lands in a buffer is f AFTER collision -- that is what makes the next
step's gather a pure stream. Both grid transfers therefore read and write
post-collision f, and the textbook factor `(tau_f/tau_c) * dx_f/dx_c` is
not the one that applies to them. Collision multiplies fneq by `(1 - 1/tau)`,
which is a different number on each level, so the post-collision ratio is
`(tau_f - 1)/(tau_c - 1) / 2`. At tau_c = 0.8 that is **-0.25 against the
+0.6875 the code was using** -- wrong magnitude and, because tau_c < 1 is
over-relaxed and tau_f > 1 is not, the opposite SIGN. Every ring cell and
every restricted coarse cell carried a viscous stress that was backwards.

AGAL has the factor right, and the reason the transcription failed is worth
keeping: AGAL's `S_Interpolate` runs BEFORE `S_Collide`
(`solver_lbm_advance.cu`), so its buffers hold post-STREAM, pre-collision f
and the textbook form is correct there. The formula transferred; the
convention it belongs to did not. This is the second time a 3D bug has come
from importing a correct 2D/AGAL expression into a different place in the
cycle, and it argues for stating the convention next to every such formula
rather than the formula alone -- which `common_d3_pool.wgsl` now does.

**How it was found, because the signature is the reusable part.**
`tools/analyze-d3-interface.js` measures total mass and total momentum over
the coarse grid alongside the bucketed field error. Beltrami is periodic and
force-free, so each level ALONE conserves both exactly, and under a refined
block `mac` holds the restricted fine moments -- an exact arithmetic mean of
rho and an exact mass-weighted mean of u -- so the sum IS the hybrid
system's total. Measured: **mass at the f32 readback floor (the same 1e-1 as
the dense and refine=all controls) while momentum drifted 1.3e+1, seven
orders above its own floor of ~1e-6, exactly linearly in t.**

That asymmetry is the whole diagnosis. fneq has no zeroth or first moment,
so a wrong fneq CANNOT perturb a mass flux -- but the second moment is the
viscous stress, which is the momentum flux. Mass-clean and momentum-dirty
says "the equilibrium coupling is fine and the non-equilibrium one is not",
and points at the rescale rather than at the addressing or the scheme. The
plan's own guess before this measurement was a generic flux mismatch, which
would have leaked BOTH.

**Measured effect of the fix** (Beltrami n=48, boxfrac=0.5, RB=4, per-bucket
velocity L2rel; `all` and `dense` have no interface and are the controls):

|---|---|---|---|
| box, pre-collision factor (the bug) | 4.00e-2 | 6.80e-3 | 1.51e-2 |
| **box, post-collision factor** | **6.90e-3** | **3.44e-3** | **4.26e-3** |
| refine=all (no interface) | - | - | 3.73e-3 |
| dense (no fine level) | - | - | 3.34e-3 |

Momentum injection fell from 0.21 to 0.034 per step, and the seam went from
12x the far field to 2x it.

**STILL OPEN: the interface is not conservative, and that is now the whole
of the residual.** With the rescale correct, a partially-refined run
converges at **FIRST order**: whole-domain L2rel at t = 0.5 t_d is
1.36e-2 / 9.02e-3 / 7.04e-3 at N = 32 / 48 / 64, ratios 1.51 and 1.28
against the 1.5 and 1.33 a first-order scheme predicts (second order would
be 2.25 and 1.78). The controls sit at 4.6e-3 / 2.3e-3 / 2.0e-3. First-order
pollution from a second-order scheme is the textbook signature of a
composite grid whose two sides compute the seam flux independently and
disagree -- Berger-Colella's original argument, and what refluxing exists
to fix.

**M4's first item, BUILT AND MEASURED 2026-09-09: the flux correction
works, conserves exactly, and is not sufficient. It ships OPT-IN
(`?reflux=1`), not on.**

What was built: `common_d3_amr_flux.wgsl` measures the mass and momentum the
FINE solver actually moved across the seam, run once per substep against the
pool buffer that substep streams; `common_d3_amr_reflux.wgsl` computes what
the COARSE step thought it moved and corrects the difference onto the
unrefined coarse cells. The seam-only recompute this section previously
proposed turned out to be unnecessary -- correcting MOMENTS rather than
substituting populations can be done post-collision, so the coarse kernel is
untouched, the pass order stands, and the correction is a surface.

**It corrects moments, not populations, and that was forced.** A fine
emission in direction e_i does not correspond to a coarse displacement e_i:
a fine cell at the +x,-y corner of a coarse cell streaming (1,1,0) lands one
fine cell over in x and back inside in y, i.e. at coarse displacement
(1,0,0). Fine emissions therefore do not partition into coarse direction
channels, and lumping a diagonal emission into a face channel conserves its
mass while discarding its transverse momentum. Mass and momentum are moments,
linear in f, and exactly what has to balance -- so they are what the
correction is written in.

**RESULT 1: conservation becomes exact.** The momentum a partially-refined
run leaks (0.034 per step, seven orders above the f32 floor) stops dead: the
drift freezes at its startup value and does not move again over 64 steps.
That is the property the correction was built for and it is delivered.

**RESULT 2: on a seam with no convex corner it also halves the error.**
`?refine=slab` was added for this -- a band refined in x spanning all of y
and z, so the seam is two FLAT faces, periodic, with no edge and no corner
anywhere. Whole-domain L2rel at t = 0.5 t_d, N = 32/48/64:

| | N=32 | N=48 | N=64 |
|---|---|---|---|
| slab, reflux off | 1.58e-2 | 1.01e-2 | 7.58e-3 |
| **slab, reflux on** | **7.90e-3** | **6.62e-3** | **6.36e-3** |
| no interface at all (`refine=all`) | 4.58e-3 | 2.29e-3 | 1.98e-3 |

**RESULT 3, the one that matters: on a seam WITH a convex corner it is far
WORSE than no correction.** `?refine=box` with reflux on reaches 2.14e-1
whole-domain at t=64 against 4.26e-3 with it off. The measured per-cell
correction there is |d(rho u)| ~ 9.4e-3 against u ~ 0.04 -- a 25%
perturbation injected every step, globally cancelling (hence conservation
still holds) and locally ruinous.

**THE CORNER DOES NOT TILE, and this is a property of the lattice rather
than a bug.** Take a coarse cell c diagonally outside a convex corner, so
the covered cells are those with x <= c.x-1 AND y <= c.y-1. On the coarse
grid exactly one channel crosses -- `f_(1,1,0)` from `c-(1,1,0)`, carrying
`w * V_coarse`. On the fine grid the only sources that can reach the fine
cells covering c sit at `(2c.x-1, 2c.y-1, *)`, and D3Q19 has no `(1,1,+-1)`,
so only `e = (1,1,0)` crosses: 2 cells in z x 2 substeps x `w * V_fine`
= `w * V_coarse / 2`. **Half.** At a flat face the fine channels tile the
coarse one exactly (4 cells x 2 substeps x V_fine = V_coarse); at a corner
they cannot. Demanding the two sides agree cell-by-cell at a corner demands
that two discretizations agree where they provably do not.

This is precisely the assumption classical Berger-Colella refluxing rests on
and that LBM breaks. Finite-volume fluxes live on faces and fine faces tile
a coarse face exactly. Lattice populations cross corners, and corner
channels do not tile. It is a plausible reason the LBM AMR literature, AGAL
included, does not reflux -- worth checking before assuming the field simply
never tried.

**Where this leaves M4.** Two separable problems, and they should not be
attacked together:

1. **The corner. THE LITERATURE'S ANSWER IS TO CHANGE THE FORMULATION, not
   to patch the balance** -- established 2026-09-09 by reading `amr-lbm.pdf`,
   which is AGAL's own paper (Jaber, Essel & Sullivan), and AGAL's source.

   ~~(a) apply the correction only where the seam is locally flat and
   accumulate the corner residual into a neighbourhood rather than a cell;
   (b) restrict refinement to corner-free seams; (c) correct only faces and
   drop the residual.~~ **Superseded.** All three are patches on a
   formulation that cannot support a local flux balance at a corner, and
   (b) is not available for a body-fitted shell anyway.

   **AGAL does not solve this and does not claim to.** Its coupling is
   structurally ours -- interpolate ghosts, step coarse, two fine substeps,
   average back -- so it inherits the same non-conservation, and its sec 3.4
   is a literature review naming the problem rather than a fix. Two
   differences, neither of which is one: it uses 2 ghost + 2 INTERFACE
   layers and averages back only the interface layer
   (`V_AVERAGE_ADVANCE = V_AVERAGE_INTERFACE`, `solver_lbm_init.cu:94`)
   where we use GHOST=2 and restrict the whole covered region -- that is
   about which fine cells still hold valid data after two substeps, not
   about flux consistency. And its sec 4.1 explicitly DECLINES the nearest
   thing to refluxing, for tooling reasons rather than correctness ones:
   Schornbaum/waLBerla notes that only the DDFs streaming INTO a coarse
   block need communicating fine->coarse, and AGAL says specifying those
   "requires additional conditionals regarding the DDF arrangement in the
   streaming kernel, which would require more complex code generation", so
   it transfers all DDFs at the interface layer instead.

   **The answer AGAL's sec 3.4 names is the VOLUMETRIC FORMULATION.** Both
   primary sources were READ 2026-09-09 (Rohde in full, Chen 1998 in the
   relevant part); what follows is from them, not from AGAL's summary of
   them.

   **Chen (1998), "Volumetric formulation of the lattice Boltzmann method
   for fluid dynamics: basic concept", Phys Rev E 58(3) 3955.** The
   mechanism, and it confirms exactly why our corner fails. Advection is a
   RIGID-BODY TRANSLATION of a cell's spatial domain by c_i: the mass going
   from cell x to cell x' is whatever lies in `D(x) INTERSECT D_-i(x')`,
   where the second is `D(x')` translated by `-c_i`. Chen's own words for
   the coefficient: "V_i(x,x') is simply the overlapping volume between two
   cells due to advection. If we had assumed the particle distribution
   inside a cell to be uniform, then the number of particles that move from
   one cell to another would just be V_i(x,x')N_i'(x,t)/V(x), which
   TRIVIALLY ADDS UP to give the total particle number."

   That is the tiling property our accounting lacks, and it is structural:
   overlap volumes of a translated cell partition space, so they tile at a
   corner exactly as at a face. There is no channel to fail to tile. He also
   states the geometric quantities are analytic "if a Cartesian (NOT
   NECESSARILY UNIFORM) mesh is used" -- non-uniform Cartesian is in scope
   from the start.

   **Rohde, Kandhai, Derksen & van den Akker (2006), IJNMF 51:439-468.**
   The practical scheme, and it avoids ever computing a different-size
   overlap. Five steps: (1) collide both grids; (2) redistribute ONE LAYER
   of coarse cells into n^D fine sub-cells at unchanged DENSITY,
   `(N_i)_f = (N_i)_c / n^D`, hence `(n_i)_f = (n_i)_c` -- no interpolation,
   no rescaling; (3) propagate on both grids, which IS the communication
   step; (4) repeat collide-fine + propagate n-1 times, with fine particles
   that have crossed into the coarse grid NOT colliding again, only
   propagating; (5) sum the n^D fine masses for the directions pointing
   TOWARD the coarse grid, giving the coarse cell's new incoming
   distributions.

   So the interface layer of coarse cells is temporarily SUBDIVIDED and
   every transfer is between equal-size cells. That is a much smaller change
   than "rewrite the solver volumetrically" -- it is localized to the
   interface. Note step 5 is direction-selective, which is the same
   observation Schornbaum makes and AGAL declines.

   **CORRECTION TO THE EARLIER FRAMING IN THIS SECTION: Rohde is MASS
   conservative, not momentum conservative.** Mass is exact by construction
   (it is the paper's title). Momentum is not: their error analysis
   "indicat[es] an error with second- and third-order terms", and the
   machine-precision momentum drift of their Figure 16 (~1e-15 over 500
   coarse steps, half-coarse/half-fine, periodic) is a case where "the error
   MAY sum to zero", not a guarantee. **Our leak is in MOMENTUM -- mass was
   already at the f32 floor before any of this work -- so Rohde alone fixes
   the half we do not have a problem with.**

   **CHEN, FILIPPOVA, HOCH, MOLVIG, SHOCK, TEIXEIRA & ZHANG (2006), Physica
   A 362(1) 158-167. READ 2026-09-09. THIS IS THE ONE.** It is the algorithm
   behind PowerFLOW, in production for a decade at the time of writing, and
   it gives **exact conservation of mass, momentum AND energy at the
   interface, at second-order accuracy.** What follows is the whole scheme,
   because it is what M4 should build.

   **Geometry.** The interface is a layer of coarse voxels having at least
   one fine neighbour, ONE coarse voxel thick, and each such voxel is
   SUBDIVIDED into n^D fine voxels -- so the interface is a layer of coarse
   and fine voxels OVERLAPPING the same space. `Inner fine voxels` are those
   not in the interface; `first layer voxels` are interface fine voxels with
   at least one inner fine neighbour.

   **Explode / Coalesce.** An `exploded state` is a post-collision state i
   in an interface coarse voxel V FOR WHICH THE COARSE NEIGHBOUR AT
   `r_V + c_i dt_c` DOES NOT EXIST. It is distributed among V's underlying
   fine voxels conserving MME, and **removed from the coarse voxel's
   dynamics**. A `coalesced state` is the matching pre-collision state in a
   fine voxel inside V; after n fine advections these fill the interface
   fine voxels, one coarse advection gathers them into V, and they are
   **removed from the fine voxels' dynamics**. The cycle is:

       explode -> (advect fine, collide INNER fine only) x n
               -> advect coarse -> coalesce -> collide coarse

   **WHY THIS CANNOT HAVE OUR CORNER PROBLEM.** It never compares two
   fluxes. Each state is MOVED from one grid's bookkeeping into the other's
   and removed from the source, so mass goes exactly one place by
   construction. The tiling question never arises, because at the interface
   the coarse voxel and its fine children ARE THE SAME VOLUME, occupied
   twice. Note also that "the coarse neighbour does not exist" makes the
   transfer direction-selective -- Schornbaum's observation, and the thing
   AGAL declined on code-generation grounds.

   **The accuracy upgrade, which is this paper's contribution.** Uniform
   explosion (the original PowerFLOW scheme, and Rohde's homogeneous
   redistribution) is exactly conservative but only FIRST order. Replacing
   it with a LINEAR distribution,

       Ndot_i^f(r_f) = Ndot_i^c(r_c) + (r_f - r_c) . F_i(r_c)        (their Eq. 2)

   gives SECOND order while still preserving exact conservation. **The
   conservation is free, and the reason matters to us**: "As long as the
   fine voxel centers are placed symmetrically in respect to the coarse
   voxel center, the distribution Eq. (2) satisfies precise conservation of
   MME ... the conservation of mass, momentum, and energy of the exploded
   state can be achieved by using an ARBITRARY vector function F_i." The odd
   part sums to zero over a symmetric set of children, so F_i is chosen
   purely for accuracy and cannot break conservation.

   **We already satisfy that precondition.** `common_d3_pool.wgsl`'s
   `fineToCoarseUnit3` places the children at `origin -+ 1/4` -- cell-centred,
   symmetric about the coarse centre. That was chosen for the interpolation
   stencil and it happens to be exactly what Eq. (2) requires.

   **F_i is NOT the plain central difference**, and the reason is a trap
   worth reading before implementing. The steady-state solution requires the
   exploded states in the first-layer voxels to REOCCUR after the jth fine
   advection for 1 <= j < n, which a gradient along c_i destroys. So: take
   the central difference only along axes PARALLEL to the interface (both
   `r_c +- dx e_a` are interface coarse-voxel centres), zero otherwise
   (their Eqs. 4-5), then PROJECT OUT the component along c_i:

       F_i^new = C_i - c_i (c_i . C_i) / |c_i|^2                     (their Eq. 6)

   And -- directly relevant to everything above -- **at CONCAVE CORNERS the
   states are exploded UNIFORMLY**, i.e. they fall back to the first-order
   distribution there rather than trying to be clever. The corner is special
   in their scheme too; it is just not a conservation problem, only an
   accuracy one.

   **NO RESCALING, AND THE MECHANISM THAT REPLACES IT.** Coalesce averages
   the ADVECTED-BUT-UNCOLLIDED fine states Ntilde_i^f, not N_i^f: "setting
   of N_i^c in the Coalesce procedure to an arithmetic average of N_i^f's
   rather than of Ntilde_i^f's would invalidate the correctness of
   non-equilibrium distributions on the coarse grid." With
   `a = (n-1)/2n` and `omega_f = 2/(1 + n(2/omega_c - 1))` there is an exact
   identity, their Eq. (15):

       1/(n omega_f) - 1/omega_c + a = 0

   which makes `N_i^neq` on the coarse grid come out correct to leading
   order with NO explicit rescale. That is what stands in for
   Dupuis-Chopard, and it explains Rohde's otherwise baffling result that
   adding the DC rescale back DEGRADED his scheme to first order. Two
   things to note: their Eq. (14) is exactly our `tau_f = 2 tau_c - 0.5` at
   n = 2, so the level->tau mapping already agrees; and n = 2 is stated to
   be the optimal refinement factor, which is what we build.

   **Validated on a case we can reproduce**: 2D flow around a circular
   cylinder in a channel (Schaefer-Turek), three nested refined rectangles
   around the cylinder, Cd / Cl / Strouhal / pressure drop against reference
   values, linear versus uniform explosion. Linear is consistently closer,
   and "the distributions in Fig. 3 show virtually no numerical artifacts
   around the interfaces". This project already owns a cylinder harness
   (`tools/validate-cylinder.js`, `benchmarks/cylinder.json`), so the
   comparison is available rather than hypothetical.

   **WHAT THIS COSTS US, honestly.** Most of the ingredients are already
   here -- the symmetric cell-centred children, `tau_f = 2 tau_c - 0.5`, a
   ring that already covers exactly one coarse cell, interp and average
   passes that become explode and coalesce. Three things are genuinely new:

   - **Interface fine voxels must not collide.** We step the whole tile,
     deliberately (GHOST=2 self-advance). That has to become "collide inner
     only".
   - **Exploded and coalesced states must be REMOVED from the other grid's
     dynamics**, per direction. This is finally the per-cell, per-direction
     refined-mask test in the coarse kernel that M3 and the reflux design
     both dodged; there is no version of this scheme without it.
   - **The DC rescale comes OUT**, which retires the bug class fixed at the
     top of this section -- but only if it is removed everywhere at once,
     since a half-converted interface would be worse than either.

   **The reflux pass built in 6545f46 is SUPERSEDED by this.** Keep it
   behind `?reflux=1` as the record of the corner measurement -- it is what
   found the tiling problem -- but do not extend it.

2. **The floor.** Even on the slab, reflux plateaus at ~6.4e-3 rather than
   converging toward the 2e-3 the no-interface control reaches -- the N=48
   to N=64 ratio is 1.04. HYPOTHESIS, not a result: the correction adds mass
   and momentum with equilibrium weights, so it contributes nothing to the
   SECOND moment, and the flux mismatch has a stress component that is
   therefore left uncorrected. Extending the correction to the second moment
   is the obvious next experiment and it is cheap -- the flux pass already
   has every population it would need.

      stays the default until 4.1c/4.1d.

      `common_d3_amr_coalesce.wgsl` (+ q19/q27 entries), `COLLIDE_RING = 0`
      in `common_d3_amr_step1.wgsl` so interface cells advect without
      colliding, the `mac`-from-pool projection folded into coalesce, and
      `?refine=bar` as the middle rung of the geometry ladder. No

      THE PASS ORDER INVERTS on this path, and that is the load-bearing
      trick: coalesce writes the fine outflux into the covered cells' slots
      of the TIME-t coarse buffer, and the coarse step then runs LAST and
      picks it up by pulling from those cells exactly as it pulls from
      anything else. No per-direction test in the hot kernel, no extra
      binding, no unfusing of stream+collide.

      **THE CONVEX-EDGE LEAK, AND THE FIX.** As first built this lost mass
      at a constant rate along every convex EDGE of the refined region --
      `box` -2.69e+1 and `bar` -1.80e+1 at t = 8, ratio 1.49 against those
      geometries' convex-edge-length ratio of 1.50, identical at RB=4 and
      RB=8, and momentum drifted with it. The cause, and it is worth
      keeping because the same shape will recur in 4.1c:

      A ring cell `p` holds, after substep B, either its interior source
      `q`'s outflux at `t + dt/2` (when `q = p - e_i` is interior) or at `t`
      (when `p - e_i` is itself a ring cell and `q = p - 2 e_i` is). The
      coalesce delivers what now sits in `coarse(p)` by writing it into the
      slot of `coarse(p) - e_i`, so the coarse pull carries it to
      `coarse(p)`. For the `t` outflux that cell is always covered --
      `coarse(p - 2 e_i) == coarse(p) - e_i` exactly. For the `t + dt/2`
      outflux it need not be: that value has moved one FINE cell, so
      `coarse(p)` may have advanced on only SOME of `e_i`'s axes, and
      subtracting `e_i` then steps back out of the refined region on the
      others. On a flat face it lands on another covered cell and the
      accounting is only smeared laterally -- which is exactly why `slab`
      measured exactly conservative and `bar`/`box` did not. At a convex
      edge it lands on the DIAGONALLY OUTSIDE cell, which is unrefined, so
      no coalesce thread claimed `p` and the value was dropped when explode
      refreshed the ring. Predicted size f/2 ~ (1/36)/2 = 1.4e-2 per edge
      coarse cell per macro-step (two grazing directions at an xy edge,
      (1,-1,0) and (-1,1,0), x two fine cells along the edge x one dropped
      population each, over the eight fine cells of a coarse cell) against
      the -1.2e-2 measured. That agreement is what identified it; the
      hand-tracing that preceded it had stopped paying.

      The fix is the ORPHAN PASS in `common_d3_amr_coalesce.wgsl`: the same
      kernel, on the cells it used to return from. Ring cell `p` in
      direction `i` is claimed by `coarse(p) - e_i`, and that cell is either
      covered (the coalesce proper) or not (the orphan pass) -- one test
      with opposite sign, so no double counting by construction. An orphan
      is ADDED to the unrefined cell's own slot: `s` is a real fluid cell
      whose `f_i` is already pulled by `s + e_i`, and the orphan is mass
      that transited `s`'s volume on its way out of the refined region, so
      it goes to the right cell in the right direction and momentum comes
      out right too.

      **REJECTED, and recorded so it is not retried: gathering by ORIGIN**
      -- summing, for each of a covered cell's own eight subcells, the two
      cells its direction-i outflux now occupies. That is also exactly
      conservative, is a smaller change, and was measured **4.6x WORSE in
      the field** (`box` whole-domain 4.58e-2 against 9.95e-3 at t = 16).
      Reason: at a convex corner six of eight subcells' diagonal outflux
      leaves the region against the coarse cell's one link, so it hands
      `c + e_i` mass that physically sits in a different neighbour.
      Conservation is necessary and not sufficient; the destination is what
      has to be right.

      whole-domain L2rel at t = 16 is 1.25e-2 against 9.95e-3 before. That

      The leak was flattering the far field by removing the injected error

- [x] **M4.1c — DONE 2026-09-10. TWO changes, and the order between them is
      the finding.** The interface is now conservative AND its field error
      has fallen to the no-interface control's level.

      **M4.1c-i — the IN-ORPHAN, the mirror of 4.1b's OUT-orphan. This is
      the one that mattered.** 4.1b left the interface exactly conservative
      and NOT CONSISTENT: it did not preserve a uniform flow. Those are
      separate requirements and the geometry ladder cannot tell them apart,
      which is why the conservation gate went green over a defect worth 8x
      the field error.

      The asymmetry: at a convex edge a coarse cell's child can cross the
      seam in ONE fine step while the coarse cell itself does not, and it
      cuts both ways.

        OUT (4.1b): a half-step EXIT that no coarse bucket can absorb.
            Dropped -> a mass leak. Added to the receiving cell's slot ->
            conservative, but that cell now gets its coarse neighbour's
            f_i PLUS the orphan, i.e. more than a uniform state can hold.
        IN (this): a half-step ENTRY that no coarse cell explodes, because
            v + e_i is unrefined. Left at zero -> the fine region gathers 0
            where it should gather v's population. NOT a leak, because v
            keeps that population and streams it coarsely -- which is
            exactly the surplus the OUT-orphan then delivers.

      So the two are one defect seen from both sides, and the fix is one
      subtraction: inject v's population into those children
      (`common_d3_amr_explode.wgsl`) and take the same amount off
      `f_coarse[i][v]`. It lands on the SAME (cell, direction) slot the
      OUT-orphan adds to, and in a uniform flow the two counts are equal, so
      the net write is exactly zero -- consistency restored with
      conservation untouched. The injection is deliberately UNIFORM even
      under EXPLODE_LINEAR: only a subset of the eight children fire, so a
      linear term would not sum out and the charge would no longer equal the
      injection.

      **M4.1c-ii — the linear explosion**, as originally specified:
      `Ndot_i^f = Ndot_i^c + (r_f - r_c).F_i`, central difference on the
      axes with two REAL coarse neighbours (which excludes the interface
      normal automatically and degrades to uniform at a concave corner --
      no geometry is classified), projected orthogonal to `c_i`. That
      projection is not cosmetic: the scheme's REOCCURRENCE property is the
      statement that the exploded field is invariant under translation by
      -c_i, and a linear field is invariant under it iff `F_i . c_i = 0`.
      With a component along `c_i` the two substeps inject different values
      from one coarse state -- a spurious time variation at the seam.
      `?explin=0` restores uniform.

      **THE ORDER IS THE FINDING.** Measured on its own, against 4.1b's
      interface, the linear explosion was a NO-OP -- box whole-domain
      2.19e-2 vs 2.23e-2, well inside run-to-run noise. It was completely
      masked: the edge inconsistency is O(1) and swamped a second-order
      term. With the IN-orphan in, the SAME change is worth a factor of two
      on every geometry. A stage that measures as a no-op is not necessarily
      wrong; it can be downstream of something bigger.

surface.

Parameterizing one shader set over `DIM` is nonetheless worse. WGSL has no
preprocessor beyond this repo's own `@include`, no templates, and array
sizes must be constant — so `array<f32, Q>` with Q varying by dimension
forces override-baked pipeline variants of every kernel anyway, and the
index arithmetic, neighbour enumeration, bilinear-vs-trilinear and
quadrant-vs-octant decode all differ structurally, not by a constant.

**Recommended middle path:**

1. **Fork the shader files** (`shaders/d3_*.wgsl`), so a 2D change cannot
   break 3D by accident and vice versa.
2. **Share the genuinely dimension-agnostic includes** where they really
   are agnostic (`common_reduce` after generalizing to 6 outputs;
   `common_fpack`'s lo/hi/word helpers after generalizing the plane count).
3. **Generate the lattice tables from a shared `.mjs`**, asserted by a
   unit test, exactly as `f-pack.mjs` + `tools/test-f-pack.js` already do.
   A transposed `opp` table is the highest-consequence, lowest-visibility
   bug available in this port.
4. **Add every 3D page to `runBootSmoke` in `tools/validate-all.js` on the
   day it is created**, not after it breaks. That check exists precisely
   because a page nothing visited stayed broken in production.

## 7. Ranked risks

1. ~~**Q=27 register spilling** (§2.4).~~ **RETIRED 2026-09-09 by M0.**
   Measured: the full kernel matches its own stream-only bandwidth ceiling
   at both velocity sets, at 77%/71% of device peak. No spill. Nothing
   downstream needs the restructuring contingency, and §2.4's numbers are
   the new anchor for every throughput figure in §3.
2. **3D 2:1 balance in `manage_pool`.** The 2D version's own header
   documents three live-verified bugs found only by
   `debugCheck21Balance`; 3D has 6 face-neighbours, 8 children, and 26
   ghost neighbours. Mitigation: port the invariant checker *before* the
   manager, and assert periodically through a run as the 2D tool already
   does — a transient violation must not slip past.
3. **Refinement threshold retuning.** The 2D thresholds will not transfer,
   and §3.3 shows a 2x wall-clock swing between sparse and generous
   refinement. This is a tuning campaign, not a constant.
4. **Memory / binding limits** (§2.2). Well-understood, and the
   raised-limit machinery exists — but it caps what resolutions are
   reachable and should be decided before the pool layout is fixed, not
   after.
5. **Coupling overhead may be worse than modelled — now risk #1 by
   default.** With M0 done this is the ONLY remaining assumption in every
   throughput figure in §3 (the solve rate is measured; the coupling
   fraction is not). 2D measures 40–49% of frame; the surface-to-volume
   argument says 3D is worse, and §3.2 assumes only "somewhat". If it lands
   at 65%, every throughput number above drops ~30%. Measurable at M3 with
   the existing `?benchSkip=` groups, which is the earliest point it can be
   known — and it should be the first thing M3 measures, not the last.
6. **Volume rendering eats the schedule.** Mitigated as planned: M1 shipped
   the slice view (`shaders/d3_render_slice.wgsl`) and the raymarcher stays
   at M6. One lesson worth carrying there: `common_vortcolor.wgsl`'s tone
   curve is calibrated for a 2D shedding wake at |omega| ~ 0.05, and every
   3D field so far is an order of magnitude gentler, so the page normalizes
   by a scenario-derived reference and pins VORT_SCALE to 1. A transfer
   function that is not normalized to the actual field renders a correct
   simulation as a black screen.
